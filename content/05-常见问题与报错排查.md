# 常见问题与报错排查

适合：通过本站使用 GPT、Claude、DeepSeek 或图片服务的用户。核对日期：2026-10-24。网页入口：`#track/help`。

本页按用户提供的错误汇总细化，并根据本站源码及官方文档修正归因。源码核验不代表线上每项配置完全相同；具体问题需结合错误原文和日志判断。

## 先做三步检查

1. **保留报错原文：** 记下错误码、提示文字和发生时间。截图前遮住密钥与个人资料。
2. **核对正在用的配置：** 确认客户端、接口地址、密钥分组和模型名称，与对应教程一致。
3. **先查记录，再决定重试：** 查看本站使用记录或任务状态。长任务报超时，也可能已经提交。

状态码是线索，需一起看 `code`、`type`、`message` 和请求 ID。HTTP 200 的流式连接也可能随后失败。

GPT / Codex、Claude Code 教程使用 `https://www.yydsapi.uno`；Canvas 生图使用 `https://image.yydsapi.uno`。不同客户端补全路径的方式不同，按对应教程填写，不统一要求加或删 `/v1`。

网页支持错误码 / 关键词搜索、4xx / 5xx / 流式筛选、展开排查和清除筛选。搜索命中后会展开处理步骤。

## 命令行连通性测试

网页入口：`#track/help?section=faq-connect`。网页提供“测试模型 ID”输入框，默认 `gpt-6.1-sol`；自定义名称实时同步到命令，复制使用当前有效名称。名称需与密钥分组可用模型一致，允许字母、数字及 `. _ - / : +`，最多 128 个字符。无效 / 空值会提示并暂停复制；密钥始终使用占位符。

此例测试 Chat Completions 接口。Codex 配置仍按 GPT 教程使用 Responses。

1. 按 **Win + R**，输入 `cmd` 并回车，打开 Windows 命令提示符。
2. 在网页输入模型 ID 并复制命令；在本机把整段 `sk-***************************` 替换成完整本站 Key。
3. 粘贴到 CMD，按 Enter。测试发起真实调用，可能产生费用。

```bat
curl.exe -X POST https://www.yydsapi.uno/v1/chat/completions --ssl-no-revoke -H "Content-Type: application/json" -H "Authorization: Bearer sk-***************************" -d "{\"model\": \"gpt-6.1-sol\", \"messages\": [{\"role\": \"user\", \"content\": \"你好，请测试一下连通性。\"}]}"
```

成功时返回 JSON，在 `choices[0].message.content` 中可见文字回复；回复内容无需固定。若返回 `error` 对象，按对应错误条目排查。命令执行结束不等于调用成功。

该 JSON 引号写法适用于 Windows CMD。保留用户给定的 `--ssl-no-revoke`：这是 Windows Schannel 的兼容选项，用于排查证书吊销检查失败；它关闭本次吊销检查，仍验证证书链和主机名，无需时可移除。

## HTTP 状态码速查

### 400 · 请求内容或格式不符合要求

**常见提示：** `Bad Request` / `invalid_request_error` / `thinking` / `signature` / `context_length_exceeded`

**先做：** 先用新对话和一句短问题检查，再核对地址与参数。

**可能原因：** 可能是参数或协议不匹配、上下文超限、历史消息不完整。Claude 思考块的 `thinking`、`signature` 或 `redacted_thinking` 被改动或丢失，或历史块与当前模型 / 账号不兼容，也可能触发 400。跨渠道切换本身不能直接证明签名失效。

**你可以先做：**

1. 保存当前任务内容，另开一个新对话，用一句短问题检查。旧对话先保留，便于排查。
2. 按对应客户端教程核对 Base URL、协议和模型。不要随意增删 `/v1`，也不要把 `/chat/completions` 与 `/responses` 的格式混用。
3. 若错误明确指出上下文或参数问题，缩短历史、减少附件，或按该模型支持的参数调整；新会话仍报签名错误时，把脱敏原文交给站方。

**站方排查参考：**

- 结合请求 ID 检查实际路径、请求体、模型映射和协议转换；对照报错字段定位，不把所有 400 都归因于用户。
- 按上游协议检查思考块与工具调用消息的完整回传、历史变更及账号约束。会话粘性只在适用部署中评估；不要伪造签名或无条件删除所有 thinking 块。

### 401 · 密钥缺失、错误或已停用

**常见提示：** `Unauthorized` / `Invalid API key` / `INVALID_API_KEY` / `API_KEY_REQUIRED` / `API_KEY_DISABLED`

**先做：** 检查客户端实际读取的 Key，尤其是旧环境变量。

**可能原因：** 本站 Key 未填写、复制不完整、含多余空格、已删除或停用，都可能导致鉴权失败。客户端也可能仍在读取旧配置。401 不能单独证明是上游账号失效。

**你可以先做：**

1. 到主站“API 密钥”检查状态，重新复制完整 Key。按原样粘贴，不手工增加或删除前缀。
2. 核对当前供应商和配置文件；若用环境变量，检查是否仍有旧 Key。修改后按工具教程重新启动。
3. 确认填写的是对应分组的本站 API Key，登录密码与其他平台的 Key 不能替代。仍失败时停止循环重试，再求助。

**站方排查参考：**

- 先查本站鉴权日志与用户状态，再核对请求头。上游认证问题应结合上游尝试日志处理。
- 本站源码的默认处理会把部分上游 401 / 403 转为 502；自定义透传规则可能不同，不能只看用户侧状态码判断上游 Key 是否失效。

### 403 · 权限、余额或访问策略限制

**常见提示：** `Forbidden` / `ACCESS_DENIED` / `INSUFFICIENT_BALANCE` / `API_KEY_EXPIRED` / `cyber_policy` / `quota` / `WAF`

**先做：** 查看余额、密钥有效期、分组权限，再读具体错误。

**可能原因：** 本站余额不足、Key 过期、分组权限失效、IP 限制或密钥用途不符，都可能返回 403。上游安全策略或 WAF 也可能拒绝请求；`cyber_policy` 不一定只出现在 403。

**你可以先做：**

1. 在控制台检查账户余额 / 订阅、Key 有效期及所属分组，确认当前模型和入口允许使用。
2. 若明确提示安全策略，按服务规则检查任务内容；合法任务疑似误判时，提供脱敏报错反馈站方。
3. 若看到网页验证、HTML 拦截页或访问被拒绝，记录时间和请求编号，由站方检查接入策略。

**站方排查参考：**

- 按错误来源分别检查余额、权限、IP 策略、WAF 误拦截及上游规则，核对合法客户端的接入方式。
- 不要把所有 quota 字样都归为 403：本站密钥额度耗尽可返回 429，需一起看错误体。

### 404 · 模型或接口路径未找到

**常见提示：** `Not Found` / `model_not_found` / `模型不存在`

**先做：** 核对模型完整 ID 与分组，不要只改一个相似名称。

**可能原因：** 接口路径不存在，或当前分组没有配置支持该模型的账户，都可能出现 404。本站可用 `model_not_found` 表示当前分组不支持此模型。

**你可以先做：**

1. 从当前分组的可用模型列表复制完整模型 ID，核对大小写、后缀和密钥分组。
2. 对照所用工具的教程检查 Base URL。模型手动加入客户端列表，并不代表获得了调用权限。
3. 名称与路径都正确仍失败时，保留原文反馈站方；重复发送相同配置通常不能修复此问题。

**站方排查参考：**

- 检查路由、模型映射、分组与模型支持关系；区分模型未配置、全部限流和暂时没有容量。

### 429 · 无效鉴权请求过多

**常见提示：** `INVALID_AUTH_RATE_LIMITED` / `鉴权失败防护`

**先做：** 暂停自动重试，修正密钥，按 Retry-After 等待。

**可能原因：** 这是本站入口的无效鉴权防护，主要按客户端 IP 汇总无效请求。填错 Key 后高频重试可能触发；共用网络出口也可能共用计数。它不等同于上游号池账号失效。

**你可以先做：**

1. 暂停正在循环重试的客户端、脚本或任务，先按 401 条目核对 Key 和实际生效的配置。
2. 响应中有 `Retry-After` 时按提示等待；具体恢复时间以实际返回和站方配置为准。
3. 正确配置后仍持续出现，记录使用的网络环境、时间和报错，联系站方检查。

**站方排查参考：**

- 检查入口无效鉴权日志、可信客户端 IP 的识别及共用出口情况；核对防护配置与 Retry-After。上游账号健康状况另查上游日志。

### 429 · 请求过快，或额度已经用完

**常见提示：** `Rate limit reached` / `insufficient_quota` / `API_KEY_QUOTA_EXHAUSTED` / `USAGE_LIMIT_EXCEEDED` / `gateway_concurrency_limit` / `gateway_queue_full` / `RPM` / `TPM`

**先做：** 先分清“速度受限”和“额度不足”，再决定是否等待。

**可能原因：** 可能触发每分钟请求数 / Token 数（RPM / TPM）、并发或排队上限，也可能是密钥额度、订阅窗口额度或上游额度耗尽。本站 Responses 路径中的 `insufficient_quota` 也可能表示本站 Key 额度用完。

**你可以先做：**

1. **速率或并发限制：**减少同时运行的任务，按 `Retry-After` 等待。脚本可使用有次数上限的指数退避与随机延迟，避免多个请求同时重发。
2. **额度不足：**检查本站 Key 限额、账户余额和订阅窗口；按实际情况补足权益、调整限额或等待窗口恢复。不断重试不会增加额度。
3. 图片 / 视频先查已有任务和消费，再考虑重新提交，避免重复生成。

**站方排查参考：**

- 检查限流层级、队列、账户可用容量和配额；区分本站额度与上游额度，给出明确错误码和适用的重试时间。

### 500 · 服务内部处理失败

**常见提示：** `Internal Server Error` / `api_error`

**先做：** 保留请求编号；持续失败时交给站方排查。

**可能原因：** 本站或上游内部处理异常都可能产生 500，涉及服务状态、协议转换、模型映射等多种情况。仅凭 500 不能确定是哪一层。

**你可以先做：**

1. 记录时间、模型、入口和请求编号。先查看任务 / 使用记录，确认后再做有限重试。
2. 若新会话中的短请求也持续失败，带脱敏错误原文联系站方。

**站方排查参考：**

- 关联网关与上游日志，检查异常栈、依赖服务、请求转换、模型映射及近期配置变更；不要只按单一原因排查。

### 502 · 网关未能取得正常上游响应

**常见提示：** `Bad Gateway` / `upstream error` / `握手失败`

**先做：** 稍后有限重试；反复重建本站 Key 通常无助于定位。

**可能原因：** 可能是上游连接、握手、反向代理或服务进程异常。本站部分默认错误处理也会把上游认证 / 账单类错误转换为 502，需要站方结合日志确认。

**你可以先做：**

1. 保留报错和发生时间，查看是否已有任务或使用记录，再稍后尝试。
2. 持续出现时反馈客户端、模型与请求 ID；不要只因为 502 就反复创建新 Key。

**站方排查参考：**

- 检查反代、服务进程 / 容器（若使用）、DNS / TLS 和上游连通性；结合错误映射与透传规则检查上游认证和账单状态。

### 503 · 服务暂时不可用或没有可用容量

**常见提示：** `Service Unavailable` / `No available channels` / `server_is_overloaded` / `API_KEY_AUTH_OVERLOADED`

**先做：** 确认模型后等待恢复，避免高频循环重试。

**可能原因：** 可能暂时没有可用账户 / 渠道、上游过载或本站鉴权服务临时过载。当前分组完全不支持模型时，本站也可能返回 404；全部可用账户被限流时可能返回 429。

**你可以先做：**

1. 先核对模型与密钥分组。响应含 Retry-After 时按提示等待，减少并发。
2. 持续不可用时联系站方；需要更换模型时，从当前分组支持的列表选择，并重新核对能力和费用。

**站方排查参考：**

- 检查容量、账户 / 渠道健康、分组绑定、临时禁用与上游负载；按日志判断是配置问题还是暂时没有容量。

### 504 / 524 · 网关或边缘代理等待超时

**常见提示：** `Gateway Timeout` / `A Timeout Occurred` / `timeout` / `超时`

**先做：** 先确认任务是否已提交，再决定是否重发。

**可能原因：** 长时间思考、生成、上传或服务过载，可能超过链路某一层的等待时限。504 与 524 需分别查网关 / 边缘代理日志；具体时限取决于实际配置。

**你可以先做：**

1. 先查看任务状态和使用记录。网页超时不代表任务一定没处理，也不代表一定没有消费。
2. 长文本可拆小任务、减少一次输出；客户端和接口都支持时使用流式响应，有助于更早收到数据，但不能保证解决所有超时。
3. 图片 / 视频按对应教程查询任务；不要向不支持流式的接口强行添加 stream 参数。

**站方排查参考：**

- 定位超时所在层，检查客户端、网关、CDN 和上游的首字节、读取间隔与总时限。调整一层不等于其他层同步改变。
- 流式请求核对缓冲与及时 flush；异步长任务评估任务查询 / 轮询。下方有 Nginx 和 SSE 维护参考。

## 流式传输与客户端报错

### PING · unknown variant 'ping'

**常见提示：** `serialization error: unknown variant 'ping'` / `Responses API` / `Codex CLI` / `反序列化`

**先做：** 这是流格式兼容问题，记录版本与原文交给站方。

**可能原因：** 当当前客户端按 Responses 事件结构解析数据，却收到不支持的 `{"type":"ping"}` 变体，可能报反序列化错误。常见排查方向是网关注入了自定义 JSON 心跳，或把其他协议的事件直接透传进 Responses 流；仍需结合实际样本确认。

**你可以先做：**

1. 记录客户端版本和完整脱敏报错，可更新官方稳定版后再检查；升级不能保证修复网关的格式错误。
2. 本站 Codex 教程保留 `wire_api = "responses"`。当前 Codex 配置仅支持 Responses，不要通过改成 Chat Completions 路径来修这个错误。
3. 把时间、模型、请求 ID 和报错交给站方；无需反复修改提示词或重建 Key。

**站方排查参考：**

- 在转换层按目标协议处理事件，避免把不支持的 JSON ping 当作 Responses 业务事件。Anthropic Messages 原生流的 ping 合法，不应全网关无差别删除。
- 需要空闲保活时，确认解析器兼容后使用标准 SSE 注释，如冒号开头的 : ping 加两个换行，并确保及时 flush；同时检查代理缓冲。

### STREAM · 生成到一半断流或输出成批出现

**常见提示：** `stream disconnected` / `connection reset` / `unexpected EOF` / `断流` / `输出中断` / `max_tokens` / `finish_reason` / `stop_reason` / `incomplete_details`

**先做：** 保存已收到的内容，区分连接中断与正常的长度停止。

**可能原因：** 网络 / 代理不稳、客户端超时、中间层缓冲或上游中断都可能影响流式输出。达到输出长度上限也会停止生成，但可能有正常的停止原因，不等同于网络断流。

**你可以先做：**

1. 先保存已收到的内容与报错。检查当前网络、代理（若使用）和客户端超时；按本站可用的正常接入方式排查。
2. 查看工具显示的终止原因。长度不足可减少本次目标或分段继续；真正连接中断时，核对记录后再有限重试。
3. 新会话和短问题也能稳定复现时，记录发生阶段、版本和请求 ID 反馈站方。HTTP 200 或已经显示部分文字，都不能单独证明请求完整成功。

**站方排查参考：**

- 检查完整的终止事件（如 response.completed / response.failed / response.incomplete）或对应协议的停止原因，区分正常长度停止和传输异常。
- 检查网络、上游读取间隔、反代缓冲、压缩与 flush。向客户端发心跳，不能证明网关仍从上游读到数据。

## 站方维护参考

### Nginx：缓冲与读取间隔

以下是现有 API 反代 `location` 中的参考片段，不是完整配置。维护者先确认实际链路，保留原有路由和鉴权，按资源与等待时长调整、校验后使用。

```nginx
# 放在现有的 API 反代 location 中
proxy_buffering off;
proxy_cache off;

# 示例值：按实际链路与资源调整
# 这是两次读取的间隔，不是请求总时长
proxy_read_timeout 600s;
```

`proxy_read_timeout` 控制两次读取间隔，不是整个请求总时长；`keepalive_timeout` 不能替代它。600s 不会自动改变客户端、CDN 或上游时限。关闭缓冲还需配合应用 flush，检查中间层压缩与缓冲。

`chunked_transfer_encoding`、`tcp_nopush`、`tcp_nodelay` 不是解决所有断流都必须照抄的组合。

### SSE：目标协议与注释心跳

Responses 与 Anthropic Messages 事件类型不同，应按目标协议转换。客户端支持标准 SSE 注释时，可发送 `: ping` 后跟两个真实换行；日志转义表示如下：

```text
: ping\n\n
```

实际发送的是换行字节，不是字母 n。它不同于 `data: {"type":"ping"}` 业务事件；需要及时 flush，并确认中间层未缓冲。注释可帮助部分空闲超时，不能保证解决所有 524、总时限或上游故障。向下游发心跳不等于网关收到上游新数据。

## 如何有效求助

复制以下模板，填写能找到的信息；没有请求 ID 就注明“未显示”。不用为了填满模板反复请求。

```text
发生时间（注明时区）：
客户端 / 页面及版本：
模型完整名称：
所用分组名称：
Base URL（不要包含密钥）：
HTTP 状态码：
错误原文（先脱敏）：
请求 ID / 任务编号（如果有）：
是否新会话 / 短请求也能复现：
已做过哪些检查：
```
